\section{Equipos de cómputo y entorno de desarrollo}
El entorno hardware en el que fueron desarrollados los experimentos de este proyecto es el Centro de Supercomputación de Galicia (CESGA). Este centro es un nodo de la Red Española de Supercomputación y datos (RES) y cuenta con una capacidad de computación total de 4.36 PetaFLOPS, estando compuesto por 357 nodos interconectados a través de una red Infiniband HDR.

Existen diferentes grupos de nodos con distintas especificaciones hardware. En concreto, estos experimentos fueron realizados en un nodo del grupo grupo
(mirar en el cesga los nodos que se usaron y completar).


El entorno de software configurado y desplegado sobre esta arquitectura de hardware consta de las siguientes especificaciones:
\begin{itemize}
    \item \textbf{Sistema Operativo:} Distribución Rocky Linux versión 8.4 (\textit{Green Obsidian}), compatible con entornos Red Hat Enterprise Linux (RHEL).
    \item \textbf{Estándar de Lenguaje:} Se empleó el estándar \textbf{C++20}.
    \item \textbf{Compilador:} Las implementaciones fueron compiladas mediante la \textit{GNU Compiler Collection} (GCC), cargando explícitamente el módulo \texttt{gcc/12.3.0}.
    \item \textbf{Directivas de Optimización y Extensiones Vectoriales:} Para la generación de los binarios ejecutables, se aplicó el nivel de optimización alta \texttt{-O2} junto con la macro \texttt{-DNDEBUG} para inhabilitar aserciones de depuración y maximizar el rendimiento. Adicionalmente, el sistema realiza un análisis de compatibilidad por hardware en el nodo de cómputo para activar de forma nativa las siguientes extensiones vectoriales:
    \begin{itemize}
        \item \texttt{-mavx2} (\textit{Advanced Vector Extensions 2}): Permite la vectorización de bucles mediante instrucciones SIMD en registros de 256 bits, procesando múltiples coordenadas de puntos 3D de forma simultánea.
        \item \texttt{-mbmi2} (\textit{Bit Manipulation Instruction Set 2}): Introduce soporte directo por hardware para instrucciones avanzadas de manipulación de bits (como \texttt{PDEP} y \texttt{PEXT}).
    \end{itemize}
    Asimismo, se habilitó la optimización interprocedural o en tiempo de enlazado (LTO/IPO) a través de CMake, forzando a GCC a optimizar el proyecto de forma global y permitiendo la inserción en línea (\textit{inlining}) de funciones entre diferentes archivos fuente.
    \item \textbf{Soporte de Paralelismo:} Se incluyó la API \textbf{OpenMP versión 4.5} encargada de la gestión y paralelización de hilos en memoria compartida. Se aplica en el código añadiendo directivas que definen el nivel de concurrencia en la inicialización de los bucles de búsqueda masiva sobre la estructura del Octree.
\end{itemize}



Aunque el descrito fue el entorno de ejecución real, se utilizó un entorno local de desarrollo para la programación y depuración del código fuente. Este entorno físico de soporte está constituido por una arquitectura de cómputo x86\_64 basada en un procesador AMD Ryzen 7 6800H de 8 núcleos físicos y 16 hilos de ejecución concurrentes y un sistema de almacenamiento de memoria caché multinivel (L1, L2 y L3 de 512 KiB, 4 MiB y 16 MiB respectivamente). 

Con el fin de compatibilizar el ecosistema de herramientas de desarrollo y mantener un entorno de terminal nativo unificado, el software se implementó sobre una capa de virtualización completa mediante el subsistema \textit{Windows Subsystem for Linux} (WSL2) bajo el hipervisor de Microsoft. Sobre esta capa se desplegó una distribución del sistema operativo Linux, concretamente Ubuntu 24.04.3 LTS. Este entorno local sirvió como plataforma de validación para el diseño de los algoritmos, la verificación de la correcta aplicación de la poda y su integración con el código original antes de su posterior despliegue y compilación en los nodos de cómputo del CESGA.

\section{Marco teórico matemático}
\subsection{Coordenadas tridimensionales}
La base de este trabajo es optimizar el cálculo de distancias entre dos puntos en un espacio tridimensional. Concretamente, se trabaja con dos figuras geométricas (cubo y esfera) que envuelven los puntos de búsqueda. En ambas se hace uso de las 3 componentes cartesianas de un punto tridimensional en las comprobaciones de vecindad:
\begin{itemize}
    \item \textbf{Kernel esférico:} Dos puntos son vecinos si la distancia $d_{ij}$ entre el centro de búsqueda es menor al radio de búsqueda.

    \begin{itemize}
        \item Fórmula de la distancia: \[d_{ij} = \sqrt{(x_i - x_j)^2 + (y_i - y_j)^2 + (z_i - z_j)^2}\]
        \item Existe vecindad si se cumple: $d_{ij} < R_{\text{búsqueda}}$
    \end{itemize}

    \item \textbf{Kernel cúbico:} Dos puntos son vecinos si la distancia entre los puntos para los tres ejes dimensionales por separado es menor al radio del cubo de búsqueda:
    \begin{itemize}
        \item Para un eje $k \in \{X, Y, Z\}$, la distancia $d_k{}_{ij}$ se define como:
\[ d_k{}_{ij} = |k_i - k_j| \]
        \item Existe vecindad si se cumple:
        \[|x_i - x_j| \le R \land |y_i - y_j| \le R \land |z_i - z_j| \le R\]
    \end{itemize}

\end{itemize}

Para potenciar la poda o el descarte de puntos sin tener que realizar esta comprobación, se hará uso de otros sistemas de coordenadas tridimensionales existentes aparte de los cartesianos: el sistema esférico y el cilíndrico.

Ambos son extensiones del sistema bidimensional polar. En estas coordenadas un punto se define a través de dos magnitudes: un radio $R$ y un ángulo $\theta$ sobre el origen. Para la proyección a 3 dimensiones, existe un sistema que añade un ángulo con respecto al plano y proyecta el valor del radio bidimensional a un radio tridimensional (coordenadas esféricas). Por otra parte, se puede incluir la componente Z, que le otorga la propiedad de altura a los puntos(coordenadas cilíndricas). 
La conversión de un punto a estos sistemas a partir de sus componentes se hace a través de las siguientes operaciones:
\begin{itemize}
    \item \textbf{Coordenadas esféricas} 
    \[
    \begin{aligned}
        R &= \sqrt{x^2 + y^2 + z^2} \\
        \varphi &= \arctan(y/x) \\
        \theta &= \arccos(z/R) 
    \end{aligned}
    \]

    \item \textbf{Coordenadas cilíndricas} 
    \[
    \begin{aligned}
        R &= \sqrt{x^2 + y^2} \\
        \varphi &= \arctan(y/x) \\
        Z &= z
    \end{aligned}
    \]
\end{itemize}

En el contexto concreto de los puntos dentro del Octree, se debe tener en cuenta que para poder operar a nivel de hoja se debe trasladar el origen de las coordenadas al centro del octree antes de realizar cualquier conversión u operación.

\subsection{Curvas de llenado de espacio}
Con el fin de optimizar la localidad espacial de los datos en memoria se introducen las curvas de llenado del espacio (SFC, \textit{Space-Filling Curves}) como herramientas de ordenación. Se encargan de forzar que aquellos puntos próximos en el espacio tridimensional se almacenen de forma contigua en la zona de memoria reservada para la nube.

El proceso requiere la discretización previa del espacio continuo de la nube de puntos. Sea una nube de puntos $P \subset \mathbb{R}^3$, se define su caja contenedora o \textit{bounding box} como la región semiabierta $B = [x_m, x_M) \times [y_m, y_M) \times [z_m, z_M)$, delimitada por sus esquinas inferiores y superiores. Fijando un nivel de subdivisión $L \in \mathbb{N}$ que determina una resolución de $N = 2^L$, se proyecta una rejilla discreta tridimensional $S_L = [0, N) \times [0, N) \times [0, N) \subset \mathbb{N}^3$, cuya cardinalidad total es de $2^{3L}$ celdas. Cada punto continuo $p = (x,y,z) \in P$ es trasladado, escalado y transformado en un elemento entero de la rejilla $S_L$ mediante la aplicación de la función suelo.

En la implementación práctica de este estudio se fija un nivel máximo de subdivisión $L = 21$. Esto permite codificar la posición tridimensional de cada celda en un único identificador entero de 64 bits (restringiendo las coordenadas discretas originales a tipos de 32 bits), minimizando la probabilidad de colisión de múltiples puntos en una misma celda sin penalizar el rendimiento del sistema. Una curva de llenado del espacio de nivel $l$ se define formalmente como la función biyectiva:
\[
\begin{aligned}
    C: S_l \longrightarrow [0, 2^{3l})
\end{aligned}\]

Para el propósito de evaluar el impacto de la localidad en el rendimiento de los algoritmos de búsqueda, se consideran dos familias de curvas de llenado del espacio recursivas:

\subsubsection{Código de Morton (Curva Z)}
La curva de Morton, o curva Z, mapea las coordenadas tridimensionales discretas mediante el entrelazado directo de sus bits a nivel de registros de la CPU. Para un punto discretizado en la rejilla cuyas coordenadas binarias se expresan como $p = (x_0 \dots x_{L-1}, y_0 \dots y_{L-1}, z_0 \dots z_{L-1}) \in S_L$, su código de Morton se calcula de acuerdo con la ecuación:
\[\begin{aligned}
    C_M(x_0 \dots x_{L-1}, y_0 \dots y_{L-1}, z_0 \dots z_{L-1}) = x_0 y_0 z_0 x_1 y_1 z_1 \dots x_{L-1} y_{L-1} z_{L-1}
\end{aligned}\]



La ventaja computacional de esta estructura radica en la velocidad y eficiencia de su cálculo. Al tratarse de un mapeo posicional directo de bits, la codificación y decodificación puede implementarse a través de operaciones lógicas de enmascaramiento (\textit{bitmasks}) y tablas de búsqueda (LUT, \textit{Look-Up Tables}).

\subsubsection{Curva de Hilbert}
La curva de Hilbert es una curva de llenado continua que elimina los saltos espaciales característicos de la curva de Morton. El cálculo del código de Hilbert se realiza mediante un proceso iterativo por nivel de subdivisión en el cual, tras extraer los bits homólogos de cada dimensión, se aplica una secuencia de transformaciones geométricas y rotaciones que dependen del estado de orientación previo y del octante evaluado.



Matemáticamente, la propiedad fundamental de las curvas de Hilbert es su continuidad en el espacio, satisfaciendo la condición de vecindad de forma que dos códigos consecutivos en el espacio unidimensional corresponden a celdas contiguas en el espacio tridimensional:
\begin{equation}
    \|C^{-1}(i) - C^{-1}(i - 1)\|_\infty = 1, \quad \forall i \in [1, 2^{3l-1}]
\end{equation}

A nivel teórico, esta curva ofrece una localidad espacial superior a la de Morton. Sin embargo, carece de una correspondencia de bits directa y requiere un algoritmo iterativo más costoso para computar las matrices de rotación. Sin embargo, debe prevalecer la calidad sobre la complejidad a la hora de calcular los reordenamientos de las nubes de puntos, ya que es una operación que solo hace falta realizar una vez. Se puede ejecutar incluso en un programa separado y cargar las codificaciones cuando se inicialice la nube.

\section{Algoritmos y estructuras de datos de partida}
En este apartado se describirán las estructuras y explicarán los algoritmos de búsqueda que se usaron como base para el trabajo y que ya fueron mencionados: el Octree lineal implementado por [1] y sus algoritmos de búsqueda iterativos con poda a nivel de nodo.

\subsection{Octree lineal}
El proceso de construcción es un proceso iterativo, en el cual se parte de un nodo raíz que contiene toda la \textit{bounding box} de la nube y divide repetidamente cada nodo terminal que contenga más de $maxLeaf$ puntos, siendo este un valor paramétrico introducido por el programador. 
Una vez finalizada la construcción se obtiene un número $N$ de nodos, separados en $nInternal$ (número de nodos internos) y $nExternal$ (número de nodos hoja). Todo el Octree está formado por el vector de puntos de la nube (reordenados mediante una curva de llenado y por lo tanto con una codificación asociada) junto con una serie de vectores persistentes que mapean las relaciones de descendencia entre nodos sin necesidad de usar punteros. Esta serie de vectores es la siguiente:

\begin{itemize}
    \item \texttt{std::vector<uint32\_t> offsets}

    Tiene $N$ elementos. La posición $i$ almacena el índice de del primer hijo del nodo $i$. Todos los hijos de un nodo están en posiciones consecutivas. En caso de ser el nodo $i$ un nodo hoja se cumple que \texttt{offsets[i] == 0}.

    \item \texttt{std::vector<std::pair<size\_t, size\_t>\>> internalRanges}
    
    Tiene $N$ elementos. En cada índice guarda las posiciones inicial y final de los puntos contenidos en él. Se usa para recorrer los puntos uno a uno en caso de llegar a una hoja que interseca con el kernel. Este es el punto de ineficiencia sobre el que se despliega este proyecto.

    \item \texttt{std::vector<Point> centers}   
    
    Cada elemento \texttt{centers[i]} contiene las coordenadas del centro geométrico del nodo $i$. También tiene $N$ elementos.

    \item \texttt{std::vector<Vector> precomputedRadii}   
    
    Tiene $L$ elementos siendo $L$ la profundidad máxima encontrada en el Octree. Almacena para cada nivel de profundidad las dimensiones de los octantes.

\end{itemize}

Este formato presenta una serie de ventajas con respecto a un Octree de punteros. Se eliminan las indirecciones que provocan fallos caché y se asegura que toda la estructura esté en un grupo de bloques de memoria contiguos. Además, se conoce y se tiene acceso a los puntos contenidos por un octante, ya sea una hoja o no, y se consigue que esos puntos estén consecutivos en memoria gracias a la reordenación por SFC.

\subsection{Algoritmos de búsqueda}

A diferencia de las aproximaciones clásicas basadas en punteros, donde el recorrido del árbol requiere desreferenciar enlaces hacia nodos hijos dispersos en el montón o \textit{heap}, el algoritmo optimizado implementado en este proyecto explota la geometría de los octantes y la contigüidad de los índices para discriminar bloques enteros de puntos.

El procedimiento general de búsqueda geométrica se rige por un esquema de recorrido recursivo sobre los nodos del árbol, evaluando la colisión espacial entre la caja del nodo actual y el volumen del kernel de consulta. El flujo algorítmico se define en los siguientes pasos:

\begin{enumerate}
    \item \textbf{Evaluación de nodos tipo rama:} Si el nodo actual del octree es una rama (nodo interno), se computa la posición relativa de su volumen geométrico respecto a las fronteras del kernel de búsqueda:
    \begin{enumerate}
        \item \textbf{Inclusión completa:} Si el octante se encuentra totalmente contenido en el interior del kernel, se activa el mecanismo de rangos internos (\textit{internal ranges}). Esto permite indexar y volcar de manera secuencial todos los puntos contenidos en dicho subárbol sin necesidad de descender más niveles ni evaluar individualmente sus elementos.
        \item \textbf{Exclusión completa:} Si el octante se halla completamente fuera de los límites del kernel, se procede a la poda (\textit{pruning}) inmediata de la rama, abortando esa vía de exploración.
        \item \textbf{Intersección parcial:} Si el octante interseca con las fronteras del kernel pero no está contenido estrictamente en él, se continúa el recorrido recursivo descendiendo hacia sus nodos hijos.
    \end{enumerate}
    \item \textbf{Evaluación de nodos tipo hoja:} Al alcanzar un nodo hoja que interseca parcialmente con el kernel, el algoritmo desciende al nivel atómico del dato, validando punto a punto mediante criterios geométricos si sus coordenadas pertenecen o no al interior del volumen de consulta.
    \item \textbf{Retorno de resultados:} Tras concluir el recorrido, se consolida y devuelve la colección de índices de los puntos que se encuentran estrictamente contenidos en el espacio delimitado por el kernel.
\end{enumerate}

Para la materialización y almacenamiento de estos índices resultantes, se han desarrollado dos variantes algorítmicas diferenciadas por su estrategia de gestión de memoria y estructuración de datos: \texttt{neighborsPrune} y \texttt{neighborsStruct}.

\subsubsection{Algoritmo \texttt{neighborsPrune}}
Esta variante implementa una estrategia de inserción directa y plana. Cuando el algoritmo identifica puntos válidos en el interior del kernel (ya sea mediante la evaluación individual en hojas o por la inclusión completa de una rama), añade cada índice de punto vecino como un elemento independiente y separado dentro de un vector dinámico estándar (\texttt{std::vector<size\_t>}). Si bien el coste de inserción es secuencial, esta aproximación puede resultar innecesaria en nubes densas, donde se insertan numerosos puntos consecutivos.

\subsubsection{Algoritmo \texttt{neighborsStruct}}
Con el objetivo de mitigar el coste de inserción masiva de elementos individuales, la variante \texttt{neighborsStruct} aprovecha la contigüidad física de los datos reordenados en memoria. En lugar de almacenar elementos aislados, define una estructura de rangos indexados mediante el tipo:
\begin{center}
    \texttt{std::vector\textless{}std::pair\textless{}size\_t, size\_t\textgreater{}\textgreater{} ranges;}
\end{center}

Bajo este esquema, cuando una secuencia de puntos consecutivos en memoria pertenece de forma unánime al kernel de consulta (caso seguro al incluir ramas totalmente contenidas), el algoritmo compacta la información realizando únicamente dos operaciones de inserción por bloque: el índice de la posición inicial y el índice de la posición final del rango. Esta técnica reduce drásticamente el espacio de almacenamiento temporal, minimiza las escrituras en memoria caché, optimizando la velocidad del algoritmo.
